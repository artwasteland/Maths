**Strategy memo for Liam and the u(24) coordinator, 5 October 2026.**

Try a disk-backed compressed filesystem in a Claude sandbox first. Put both the entire worker output base and Python's temporary directory on it, and run the existing 1,920-slice worker without changing its sources, checker pin, evidence policy or judge. This has the best chance of removing the disk obstacle without creating a new mathematical evidence route. If mounting is unavailable, or actual compression leaves too little headroom, use a reviewed partition below the dominant level-12 roots. Keep a compressed filesystem image on the desktop's SD card as another route that needs no rented account, subject to its RAM and speed limits.

**The estimates need an explicit boundary.** The supplied 36 to 39 GB dominant-piece estimate is a scenario, not an upper bound on these four u(24) runs. The builder says exactly this in [codex-u24-refine.log:108026](<repo>:108026) and [codex-u24-refine.log:108030](<repo>:108030). It applies an old cell's share to an assumed footprint. In the calculations below, let `D` be accumulated logical run bytes, `X` the largest additional live temporary footprint, `P` the shared prefix, `R` the measured effective compression ratio, and `T` the dominant subtree's time. Operational thresholds must be calculated from bytes: the runbook's default reserve is **5 GiB**, despite its variable name ending in `GB`.

Write the per-cell quantities as `G` full graph bytes, `H` reach bytes, `K` kept bytes, `U` UNKNOWN bytes, `C` final certificate bytes, `F` filter JSONL bytes, `S` filter-survivor graph bytes, `Q` triangle JSONL bytes, and `V` triangle-survivor graph bytes. A useful completed-cell approximation is:

`2G + H + K + U + C + (H + 2F + S) + (S + 2Q + V) + destination-parent copies + metadata`.

The first `2G` counts augmentation shards and their aggregate. The two `F` and two `Q` terms count part verdicts plus concatenations. This excludes prefix seed intermediates, live checker work and interrupted-write debris. It is an accounting formula, not a claim that any particular term dominates s344. A large triangle witness can be stored in a part, in the rule aggregate and in the final certificate. A graph can also appear in several levels and destination-parent files. Counts of kept graphs alone miss most of this.

**Disk-backed Btrfs compression is the first strategy that survives the objections.** The exact change is environmental: make a new bounded loop image on the sandbox's existing disk, format it as Btrfs, mount it with `compress=zstd:1` or `compress=zstd:3`, and set `U23_OUT` to a directory on that mount. Put prefix, runs, `.replay`, logs and `TMPDIR` there together. Keep results and receipts inside the repository for normal git return. Leave all frozen source bytes and the checker pin unchanged. Enable compression before any run data are written.

Btrfs offers ordinary seekable files, hard links and transparent compression; its compression units are 128 KiB. Whole-file zstd is therefore an optimistic proxy unless tested in chunks and on the actual mount. The relevant behavior is documented in [Btrfs compression](https://btrfs.readthedocs.io/en/latest/Compression.html). Use normal compression first and verify actual allocation. If its heuristics skip these files, test `compress-force=zstd:1`; it still stores incompressible blocks uncompressed and costs CPU. Do not set NOCOW or disable data checksums, which disable compression.

Expected occupancy is `(D + X)/R + filesystem overhead + small uncompressed result/host files`. With the illustrative D and an effective ratio of 2, the retained tree takes 18 to 19.5 GB; a planning envelope of roughly **20 to 26 GB** allows several GB for temporary work and metadata. At ratio 1.7, the tree alone takes 21.2 to 22.9 GB. At ratio 3, it takes 12 to 13 GB. These are conditional envelopes. A 70 GB run at ratio 1.7 does not fit.

Size the image from measured `df -B1`, leaving at least 6 GiB on the host. A roughly 28 GiB image is a plausible starting point on the described clean sandbox, provided metadata, temp work and the internal 5 GiB restart reserve fit. A sparse image saves initial allocation, not maximum capacity. Never create a 100 GB virtual device over a 39 GB host and treat its `df` as real headroom. The bounded image limits backing consumption; still monitor host space and Btrfs data/metadata space. Deletion inside a loop filesystem need not immediately shrink the host image's allocated size, so keep that same bounded image for successive slices rather than accumulating images.

For time, budget **about 5 to 7 hours on the reference three-core workload**, possibly less on four cores, plus any unmeasured unusually slow checking. This is a provisional allowance of up to roughly 40% over the supplied T, not a benchmark. Compression adds CPU but reduces I/O. Revalidation on resume also costs time. No extra monetary cost within the existing Claude fleet; allow one bounded deployment probe and one initial heavy attempt, not four blind attempts.

Add a small operational note with mount options, kernel version, physical peaks and completed-stage times. Review the mount/resume/cleanup wrapper as storage infrastructure, not a new pruning theorem.

Fatal objections addressed: sudo does not establish `CAP_SYS_ADMIN`, loop access or Btrfs support; a mount can fail. Compression does not reduce Python objects or witness-verification CPU. The checker might exceed one entire time window. A container wipe still destroys the image. A metadata ENOSPC can precede the nominal data limit. These are reasons for a probe, explicit reserves and a backup route, not reasons to weaken acceptance.

Probe, at most 2 minutes for capabilities and 20 minutes for workload: in a disposable Claude task directory create a 256 MiB image with `truncate -s 256M`, run `mkfs.btrfs`, attempt `sudo -n mount -o loop,compress=zstd:1`, and write, hash, seek, hard-link and atomically rename a small file. Bound mount commands with 10-second timeouts. Unmount, remount the same image and confirm hashes/link behavior. If utilities are missing, report that separately from permission denial; do not let package installation consume an unbounded probe. Inspect `/dev/fuse` and zram availability within the same two-minute budget, recording that existence alone does not prove usability. On the successful mount, copy at most 512 MiB of real light-run graph/certificate data, measure allocated bytes and a checker pass with sampled `TMPDIR` occupancy, then exercise an interrupted/restarted light run. The biggest immediate unknown, whether the sandbox can provide transparent compressed storage, gets a definite answer. No small probe establishes the eventual monster's total D.

**FUSE can substitute only if it passes the complete file interface test.** The exact storage change would be a read/write compressed FUSE mount at `U23_OUT`, with the same `TMPDIR` arrangement. It must expose uncompressed `st_size`, regular files, hard links, atomic rename, append/truncate and efficient seeking. The replay really seeks, and the inventory rejects symlink stubs. An archive mounter or a ZIP filesystem that rewrites the whole archive is not an adequate substitute.

At a measured ratio of 2, occupancy could again be **20 to 26 GB**, provided decompression caches and rewriting never create a second raw large file. Budget **5 to 10 hours** as an unbenchmarked allowance; userspace compression, context switches and random reads can be appreciably slower. Cost is zero in subscription compute, but potentially substantial implementation/review time. Frozen tools and ordinary judge rules need no changes if the filesystem is truly transparent.

The fatal objection is an implementation that emulates seeking by decompressing a multi-GB file into a cache, or lacks hard links. That recreates the wall, sometimes in RAM. Do not build a bespoke FUSE filesystem for these four slices as the first response. A packaged, existing implementation survives only after a 2-minute actual mount test, then a 20-minute copy/seek/link/rename/truncate test and unchanged-checker comparison on a light fixture. Its daemon must survive timeslice deadlines and be remounted before recovery; the supervisor must not kill the storage daemon while a writer is still shutting down. If no suitable implementation is already available, treat this route as unestablished.

**Zram and tmpfs are auxiliary capacity, not a replacement for the disk.** A whole 36 to 39 GB run at ratio 2 requires 18 to 19.5 GB of compressed RAM before any processes, already beyond the 15 GB sandbox. Even ratio 5 uses 7.2 to 7.8 GB, leaving a precarious budget for pruning, replay and checker objects. Ordinary tmpfs is not compressed; it stores pages in RAM and optionally swap. Zram compression works on blocks, so the whole-file certificate ratios above do not establish its ratio. See [kernel tmpfs documentation](https://docs.kernel.org/filesystems/tmpfs.html) and [kernel zram documentation](https://docs.kernel.org/admin-guide/blockdev/zram.html).

The exact viable variant is a **small, capped 1 to 2 GiB RAM contribution**, such as `TMPDIR` on a bounded tmpfs or an independently mounted zram filesystem, while the large persistent run stays on disk. It can shift perhaps 1 to 4 GB of logical temporary data at an actual block ratio of 1 to 2. Monetary cost is zero; provisional wall time remains about T, potentially worse if RAM pressure causes reclaim. Frozen sources and judge rules stay unchanged. Bound zram's actual memory consumption, not only its advertised disksize, and observe cgroup limits as well as `MemAvailable`.

Fatal objections: the worker stops below 1,536 MiB available memory; its guard does not make preallocated compressed data free. A large single-cell checker temporary can exceed a small tmpfs and fail. Zram modules, devices, mount or swap permissions may all be unavailable. Volatility adds no protection against a wiped sandbox. A two-minute actual device/mount probe, followed by a ten-minute bounded 128 MiB corpus test and observed checker transient, can settle whether this auxiliary shift is useful. Reject whole-run RAM storage under these specifications.

**Compressing finished files into `.zst` files is not transparent.** The frozen programs open the original `.g6` and `.jsonl` names as plain files. Rename-and-compress makes them absent or unreadable. A symlink to a pipe or decompressor fails inventory and cannot satisfy replay seeks, file lengths and hashes. Restoring every raw file before the final checker recreates D and merely postpones the wall.

A transparent block-addressable compressed backing store at the original paths reduces to the Btrfs/FUSE strategies above. A different possible change is a new stage controller that decompresses only a cell's working set, calls unchanged low-level programs, collects checked cell evidence and compresses it again. Expected peak becomes `compressed archive + largest raw working set`, not zero. At R=2 this starts with 18 to 19.5 GB of archive and adds that working set; budget 6 to 10 hours provisionally. It cannot drive the present frozen worker/checker as a whole, which expect the complete tree and later rescan it. It needs a new evidence protocol and coverage judge. Cost is zero compute money, considerable code/review work. A 20-minute two-cell fixture can demonstrate the protocol, but it offers no advantage over a working compressed filesystem and is not recommended.

**Earlier cleanup has a narrow viable form and a broad invalid form.** Never remove completed levels' full, reach, keep, UNKNOWN, certificates, parent concatenations or augmentation shard payloads before the present worker accepts. Replay and chain checking require the main files; evidence.py additionally counts and hashes shard payloads and parent files. A checker accepting shard manifests does not imply the worker accepts missing shards. References are [verify-chain-u24.py:548](<repo>/research/unit-distance-22/enum/verify-chain-u24.py:548), [verify-chain-u24.py:677](<repo>/research/unit-distance-22/enum/verify-chain-u24.py:677), and [evidence.py:255](<repo>/research/unit-distance-24/tools/evidence.py:255).

The plausible cleanup is only **redundant `_prune` payloads of already completed, accepted cells**. Preserve every `triangles-*.stderr` and preferably all diagnostic logs. The eventual checker uses final certificates, not old filter/rule payloads. Completed-prune resume validates source plus final certificates/keep/UNKNOWN and their verdict-derived counts, not the old filter payloads: [run-dag2.py:713](<repo>/research/unit-distance-22/enum/run-dag2.py:713). The prune manifest itself records hashes of several scratch outputs at [prune.py:1114](<repo>/research/unit-distance-22/enum/prune.py:1114); their removal should be documented, not concealed.

Exact change: an opt-in outer housekeeping step, under the existing single-writer lock and after confirmed process-tree shutdown, verifies successful prune/verification manifests and final output hashes for each completed cell, then removes only an explicit scratch-payload allowlist. Do not apply it to an unfinished cell, prefix files, or a failed cell. Keep a small hash/byte ledger of the removed scratch files outside the strict retained-result directory. This is analogous to the accepted checker chunks already deleted by prune.py, but requires an explicit lifecycle review because the frozen worker currently inventories the scratch files that remain. The checker, generator, runbook and worker sources can remain byte-identical. There is no new piece identity; review how the coordinator binds the housekeeping ledger and whether its inventory policy needs an additional rule. Test the actual retained-bundle audit rather than relying on that inference.

Savings are `completed _prune payload bytes`, excluding diagnostics. Peak is still at least **current largest cell's complete scratch + primary files + X**, plus accumulated primary files. In a scenario where 40% to 60% of D is removable old scratch, retained bytes fall to roughly **14 to 23 GB**, then the largest active cell/transient must be added back. Those percentages are a sensitivity example, not measured composition. Wall time is roughly T plus validation scans; interruptions of completed cells retain normal resume behavior. Monetary cost is zero, review cost moderate.

Fatal objection: if the largest cell itself creates the wall before completing, between-window cleanup arrives too late. Deleting all `_prune` also erases the silent-pass diagnostics and fails the evidence audit. An active cleanup sidecar introduces races. This strategy survives only as a reviewed, measured supplement. A 20-minute light-run experiment in a writable copy can compare receipts, retained audits and resume before/after the exact allowlist, with red cases for unfinished cells and deleted diagnostics. Its inventory also settles the achievable savings. Do not announce a disk solution from `_prune`'s name alone.

More aggressive cleanup would change frozen `prune.py`: unlink filter part inputs/verdicts after their concatenation is closed, and rule part inputs/verdicts after their concatenation is closed, preserving part stderr; later remove aggregates only after final certificates have passed their checker. This reduces intra-cell duplication but can sacrifice finished-part recovery after a killed prune, including hours of re-filtering. It needs independent review of concatenation, restart behavior, output equivalence and new producer hashes, plus a coordinator exception for the changed tool. The final checker can stay pinned.
